# 블록 03 — 구독 관리 + 해지 피드백

> 유료 회원의 구독 상태를 보여주고, 해지 시 이유를 수집해 이탈을 줄이는 블록

---

## A. 목적

한 문장으로: **"유료 회원이 자기 구독을 한눈에 이해하게 하고, 해지 순간에 한 번 더 물어봐서 이유를 남기게 한다."**

두 가지 목표가 겹쳐 있다:

1. **정보 제공** — 내가 어떤 플랜을 언제까지 쓰는지, 다음 결제일은 언제인지, 어떤 카드로 결제되는지를 애매하지 않게 보여준다.
2. **이탈 관리** — 해지 자체를 막지는 않되, 해지 직전에 사유를 수집하고 한 번 더 생각할 기회를 준다. 수집된 사유는 프로덕트 개선의 1차 입력이 된다.

"해지를 어렵게 만드는 다크패턴"과 "해지를 그냥 1클릭으로 처리하는 것" 사이의 중간 지점을 잡는다.

---

## B. 입력값

### B-1. 서버에서 받아오는 데이터

```ts
type SubscriptionPayload = {
  status: 'NONE' | 'ACTIVE' | 'CANCEL_SCHEDULED' | 'EXPIRED'
  plan: {
    code: 'BASIC_MONTHLY' | 'BASIC_ANNUAL' | 'PLUS_MONTHLY' | 'PLUS_ANNUAL' | null
    displayName: string | null
    tier: 'BASIC' | 'PLUS' | null
  }
  period: {
    startedAt: string | null       // 구독 시작일
    validUntil: string | null      // 유효기간 (다음 결제일 또는 해지 예정일)
    nextBillingAt: string | null   // 다음 결제일 (CANCEL_SCHEDULED면 null)
  }
  paymentMethod: {
    type: 'CARD' | 'VIRTUAL_ACCOUNT' | 'KAKAOPAY' | null
    masked: string | null          // "국민카드 ****-1234"
  }
  history: Array<{
    id: string
    paidAt: string
    amount: number
    planDisplayName: string
    receiptUrl: string | null
  }>
  coupon: {
    available: boolean             // 체험권 입력 가능 여부
    activeCouponName: string | null // 적용 중인 쿠폰
  }
}
```

### B-2. 유저 컨텍스트

- 로그인 여부
- 회원가입 경로 (이메일/카카오/Apple) — 해지 후 재가입 안내 문구 분기에 사용
- 환경 (웹/iOS 웹뷰/Android 웹뷰) — 앱스토어 결제 건은 해지 플로우가 다름

### B-3. 정적 설정

- 플랜 메타데이터 (가격, 혜택 목록)
- 해지 사유 목록 (아래 D-3 참고)
- 이력서 경험에서 가져온 `internal_utm_source` 체계 — 어느 내부 경로로 들어왔는지 태깅

## C. 상태

블록이 가질 수 있는 모든 상태를 나열한다. **"이 상태에서 무엇이 보이고, 무엇을 할 수 있는가"**가 명확해야 구현 중에 흩어지지 않는다.

### C-1. 최상위 상태 (구독 상태별)

| 상태 | 조건 | 보이는 것 | 가능한 행동 |
|---|---|---|---|
| `NONE` | 유료 구독 이력 없음 | 업셀 배너, 플랜 비교 CTA, 체험권 입력 필드 | 플랜 둘러보기, 체험권 코드 입력 |
| `ACTIVE` | 유효한 구독 보유 | 플랜명, 다음 결제일, 결제수단, 결제이력 | 결제수단 변경, 이력 펼치기, **해지하기** |
| `CANCEL_SCHEDULED` | 해지 신청했으나 유효기간 남음 | "YYYY.MM.DD까지 이용 가능" 배너, 해지 철회 버튼 | 해지 철회 |
| `EXPIRED` | 해지 완료, 만료됨 | `NONE`과 동일하되 "이전 구독 기록" 섹션 추가 | `NONE`과 동일 |

### C-2. 해지 플로우 내부 상태 (ACTIVE에서 "해지하기" 클릭 후)

해지는 1단계가 아니라 **3스텝 모달**로 다룬다. 각 스텝에서 뒤로 가기가 가능하다.

```
[ACTIVE]
   │
   │ (해지하기 클릭)
   ▼
[STEP_1: 해지 사유 선택]       ← 라디오 1개 필수, "직접 입력" 선택 시 textarea 표시
   │                            텍스트 200자 제한
   │ (다음)
   ▼
[STEP_2: 해지 확인]             ← "정말 해지하시겠어요?" + 유효기간까지 이용 가능 안내
   │                            + 구독 시 받던 혜택 재노출 (되돌리기 유도)
   │ (해지 확정)
   ▼
[SUBMITTING]                   ← 버튼 disabled, 스피너
   │
   ├── 성공 ──▶ [STEP_3: 해지 완료] ── (확인) ──▶ [CANCEL_SCHEDULED]
   │
   └── 실패 ──▶ [STEP_2 + 에러 토스트]
```

### C-3. 비동기 상태

- **로딩** — 초기 진입 시 스켈레톤
- **에러** — 구독 정보 조회 실패 시 재시도 버튼 노출
- **제출 중** — 해지 API 호출 중, 버튼 disabled + 중복 클릭 방지
- **네트워크 단절** — Mutation 실패 시 사용자 입력(사유/메모)을 날리지 않고 복원

### C-4. 특수 케이스

- **앱스토어 결제 구독자** — 해지 버튼을 노출하지 않고 "Apple/Google에서 해지해주세요" 안내로 대체
- **체험권 사용 중** — 해지 시 "체험 기간이 종료되며 유료 결제가 진행되지 않습니다" 추가 안내
- **결제 실패 직후** — 카드 변경 유도 배너를 구독 상태 위에 겹쳐 표시

## D. 행동

### D-1. 조회 행동

- 구독 카드 기본 보기
- 결제 이력 펼치기/접기 (기본 3건, "더 보기" 시 전체)
- 영수증 링크 클릭 → 새 탭

### D-2. 변경 행동

- 체험권 코드 입력 → 검증 → 적용/에러
- 결제수단 변경 → 외부 PG 페이지로 이동 (블록 범위 외)

### D-3. 해지 행동 (핵심)

**해지 사유 선택지 (일반화한 예시, 총 7개 + 직접 입력)**

1. 콘텐츠가 기대와 달랐어요
2. 아이가 잘 사용하지 않아요
3. 가격이 부담돼요
4. 다른 서비스를 쓰기로 했어요
5. 잠시 쉬었다가 다시 올게요
6. 기술적 문제가 있었어요
7. 기타 이유가 있어요
8. 직접 입력 (textarea, 선택 시 활성화)

> **사유 수 결정 이유**: 너무 적으면 "기타"에 쏠려 분석 가치가 떨어지고, 너무 많으면(10개 이상) 사용자가 읽기 전에 체크해버린다. 7개 + 직접 입력이 균형점. "잠시 쉬었다가 다시 올게요"처럼 **긍정적 재가입 여지**를 주는 선택지를 하나 끼워 넣는다.

**해지 철회**

`CANCEL_SCHEDULED` 상태에서 "해지 철회" 버튼 → 확인 모달 → API 호출 → `ACTIVE` 복귀. 철회는 유효기간 만료 전까지만 가능하다.

### D-4. 계측 이벤트 (GA4)

```
subscription_view              { status, plan_code }
subscription_history_expand    {}
coupon_apply_attempt           { code_prefix }       ← 코드 전체는 전송 금지
coupon_apply_success           {}
coupon_apply_error             { error_code }

cancel_flow_start              { plan_code, days_used }
cancel_reason_select           { reason_id }         ← 직접 입력 텍스트는 별도 필드
cancel_step_view               { step: 1 | 2 | 3 }
cancel_abandon                 { last_step, reason_id? }  ← 모달 X 버튼으로 이탈
cancel_submit                  { plan_code, reason_id }
cancel_success                 { plan_code, reason_id, had_free_text: boolean }
cancel_revoke                  { plan_code, days_remaining }
```

**`cancel_abandon` 이벤트가 E에서 말하는 "해지 포기율"의 핵심 입력**이다. 사용자가 해지 모달을 열었으나 완료하지 않고 닫은 순간을 잡아야 한다.

## E. 성과

### E-1. 핵심 지표

| 지표 | 정의 | 방향 |
|---|---|---|
| **해지율** | 월간 `cancel_success` / 월초 `ACTIVE` 수 | ↓ 낮추기 |
| **해지 포기율** | `cancel_abandon` / (`cancel_flow_start`) | ↑ 높이기 (선택지가 망설임을 만들었다는 신호) |
| **해지 사유 분포** | `reason_id`별 비율 | 관찰 (프로덕트 우선순위 입력) |
| **체험권 전환율** | 체험권 사용자 중 유료 결제 전환 비율 | ↑ 높이기 |
| **재가입률** | 해지 후 N일 이내 재구독 | ↑ 높이기 |

### E-2. 보조 지표

- 스텝별 드롭오프 (STEP_1 → STEP_2 → STEP_3)
- 해지 후 철회율
- 직접 입력 사유 길이 중앙값 (짧으면 형식적, 길면 진성 피드백)

### E-3. 주의할 점

- 해지율을 무조건 낮추는 것이 목표가 아니다. 다크패턴으로 해지를 막으면 단기 해지율은 떨어지지만 **신뢰가 깨지고 재가입률이 함께 떨어진다.** 해지 사유 분포와 재가입률을 함께 본다.
- 해지 포기율이 **지나치게 높으면** 사유 선택 UI가 혼란스럽다는 신호일 수 있다. 일정 수준(예: 30%)을 넘으면 UX 재점검.

## 핵심 설계 판단

### 판단 1. 왜 해지를 3스텝 모달로 쪼갰는가

1스텝 — 사유 수집, 2스텝 — 확정, 3스텝 — 완료. 3스텝으로 쪼갠 이유는 **사유 수집과 의사 확인을 분리**하기 위함이다. 하나로 합치면 사용자가 사유를 대충 고르고 바로 해지한다. 분리하면 사유 선택 후 "정말 해지할까?"를 다시 묻게 되고, 이 시점에 **한 번 더 생각하는 시간**이 생긴다. 이게 해지 포기율로 잡힌다.

반대로 4스텝 이상은 피했다. 스텝이 많아질수록 다크패턴에 가까워지고, 사용자는 "해지가 어렵다"고 느낀다.

### 판단 2. 왜 "잠시 쉬었다가 다시 올게요"를 넣었는가

해지 사유 중 **재가입 가능성이 암시된 선택지**가 있으면, 해지 완료 화면에서 "재가입 시 알림 받기" 같은 재진입 경로를 자연스럽게 제시할 수 있다. 같은 이유로 "다른 서비스를 쓰기로 했어요"를 넣었다 — 경쟁 서비스 이탈은 프로덕트 전략의 1차 관심사다.

### 판단 3. 왜 플랜 비활성 처리를 상위 구독자에게 적용하는가

`ACTIVE`(PLUS) 상태인 사용자가 BASIC 플랜 카드를 클릭하면 **비활성**으로 처리하고 "이미 상위 플랜 이용 중"을 노출한다. 다운그레이드 요청은 별도 고객센터 플로우로 뺀다. 이유는 다운그레이드는 결제·환불 계산이 복잡해 프런트에서 바로 처리하면 **상태 전이 누락으로 장애가 나기 쉽기** 때문이다. API 계약 단계에서 이 분기를 명확히 해야 구현 이후 수정 루프가 줄어든다.

### 판단 4. 왜 해지 직전 모달에 혜택을 재노출하는가

사용자가 해지를 결정한 이유는 대개 **혜택의 가치를 잊었거나**, **실제로 사용하지 않아서**다. 전자는 혜택 재노출로 잡을 수 있고, 후자는 어차피 해지 후 재가입 경로로 가야 한다. 혜택 재노출은 "한 번 더 생각하기" 장치일 뿐, 해지를 막는 장치가 되면 안 된다. 따라서 **스크롤 없이 보이는 최소한**만 노출하고 해지 버튼은 그 바로 아래 배치한다.

## 구현 시 주의사항 (프론트엔드)

1. **낙관적 UI 금지** — 해지 API는 실패 시 사용자가 바로 당황한다. Mutation 성공 응답을 받은 후에만 STEP_3로 전환.
2. **중복 제출 방지** — 제출 버튼은 첫 클릭 즉시 disabled. 네트워크 에러 시에도 자동 재시도 하지 않고 사용자에게 재시도 버튼 제공. 해지는 **멱등하지 않은 인식**이 강한 액션이라 자동 재시도가 "내가 두 번 해지했나?"라는 불안을 만든다.
3. **사유 데이터 보존** — STEP_2에서 뒤로 가도 STEP_1에서 선택한 사유는 유지. 모달을 X로 닫은 경우에도 세션 동안은 유지(세션 스토리지는 쓰지 않고 상위 컴포넌트 state).
4. **접근성** — 해지는 중대한 액션이므로 포커스 트랩과 ESC 처리가 필수. 확인 버튼은 tabindex로 마지막에 배치해 엔터 키로 실수 해지 방지.
5. **계측 누락 방지** — `cancel_flow_start`와 `cancel_abandon`을 쌍으로 관리. 플로우 시작만 잡히고 끝이 안 잡히면 세션 만료로 간주해 일정 시간 후 자동으로 `cancel_abandon(timeout)` 발화.
