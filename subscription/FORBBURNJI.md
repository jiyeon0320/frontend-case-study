# FORBBURNJI.md

> Block 03 — 구독 관리 + 해지 피드백 프로토타입에 관한 내부 문서

이 폴더는 포트폴리오용 블록 설계 문서 하나(`BLOCK_03_subscription_cancel.md`)와 그 설계를 실제로 굴러가게 만든 HTML 프로토타입 하나(`prototype.html`)로 이루어져 있다. 둘이 한 쌍이다. 문서만 있으면 "그래서 실제로 어떻게 움직이는데?"라는 질문에 못 답하고, 프로토타입만 있으면 "왜 이렇게 만들었는데?"라는 질문에 못 답한다. 그래서 둘이다.

---

## 1. 기술 아키텍처 — 한 페이지짜리 프로토타입이 왜 이렇게 생겼나

이 프로토타입은 **단일 HTML 파일**이다. 서버도 없고 빌드 스텝도 없다. 브라우저에서 열면 바로 돈다. 왜 이렇게 만들었냐면 — 포트폴리오 뷰어가 `npm install`을 하고 싶어 하지 않기 때문이다. 파일 하나 받아서 더블클릭하면 끝나야 한다.

그래서 선택한 구조는 이렇다:

```
prototype.html
├── <style> ────────── CSS 변수 기반 디자인 토큰 (루트 :root에 집중)
├── <main> ─────────── 3가지 구독 상태를 모두 한 문서에 담고 display로 전환
├── <modal> ────────── 해지 플로우 3스텝 (step-progress 바 + 3개 .modal-step)
├── <dev-panel> ────── GA4 이벤트 로그 (오른쪽 아래 검은 패널)
└── <script> ───────── 바닐라 JS, 프레임워크 없음
```

**왜 리액트가 아닌가.** 실무 코드는 Next.js 15 App Router + Apollo Client + TypeScript다. 하지만 프로토타입은 "이 블록이 어떻게 움직이는지"를 보여주는 게 목적이고, 리액트로 만들면 빌드·호스팅·의존성 관리가 끼어든다. 15분 안에 작동하는 걸 보여줘야 면접에서 쓸모 있다. 프레임워크 대신 **display 전환**과 **전역 state 변수 몇 개**로 state machine을 흉내 냈다.

**상태를 display로 흉내 내는 법.** 실제 서비스라면 URL query나 전역 스토어가 상태를 쥐고 있겠지만, 여기서는:

- 구독 상태 3개(`ACTIVE` / `CANCEL_SCHEDULED` / `NONE`)를 `.view` div 세 개로 미리 렌더링
- 상단 토글 버튼이 `.view.active` 클래스만 바꿈
- 해지 모달의 스텝 3개도 `.modal-step` div를 `display: none/block`으로 전환

이게 실무에서 권장되는 패턴은 아니다. 하지만 프로토타입의 제약(파일 하나, 빌드 없음)에서는 가장 빠르고 읽기 쉽다. 실무에선 Zustand나 URL state로 갔을 거다.

## 2. 코드베이스 구조 — 연결 관계

```
블록 03/
├── BLOCK_03_subscription_cancel.md  ← "왜 이렇게 설계했는가" (A~E 5축 + 판단 근거)
├── prototype.html                    ← "실제로 이렇게 동작한다"
└── FORBBURNJI.md                     ← 이 파일 (기술 문서 + 회고)
```

**문서와 프로토타입의 연결.** `BLOCK_03_*.md`에서 정의한 것들이 `prototype.html`에서 어떻게 구현됐는지 매핑해두면 이렇다:

| 설계 문서에서의 정의 | 프로토타입에서의 구현 |
|---|---|
| C-1 최상위 상태 4개 | `.view[data-view="..."]` 3개 (EXPIRED는 생략, NONE과 거의 같아서) |
| C-2 해지 플로우 3스텝 | `.modal-step[data-step="1|2|3"]` + `.step-progress .step-bar` |
| D-4 계측 이벤트 목록 | JS의 `track(name, params)` 함수 + 우측 하단 dev panel |
| E 성과 지표 | 우측 사이드바의 metrics-card (데모 값) |

dev panel은 사실 포트폴리오 프로토타입의 **숨은 주인공**이다. 면접관이 해지 모달을 조작하면 패널에 `cancel_flow_start`, `cancel_reason_select`, `cancel_abandon` 같은 이벤트가 실시간으로 찍힌다. "계측을 설계할 줄 안다"를 말로 설명하는 것과 직접 보여주는 건 다르다.

## 3. 사용한 기술과 그 이유

### 타이포그래피 — Fraunces + IBM Plex Sans KR

왜 이 조합인가. **어린이 도서 플랫폼의 톤을 살리면서, 프로덕션 프로덕트의 엄격함도 같이 가져가고 싶어서**.

- **Fraunces (제목)**: opsz(optical size) 축을 지원하는 가변 세리프체. 큰 크기에서 우아하게 들어가는 디테일이 있어 "따뜻함"을 잡는다. 아동 친화적인 세리프체를 쓰되 유치하지 않게.
- **IBM Plex Sans KR (본문)**: 한글 고딕 중 가독성과 톤 밸런스가 가장 안정적. 국내 대기업 서비스들이 자주 쓰는 Pretendard도 훌륭하지만, **Plex는 영문 페어링이 자연스럽고 모노스페이스 변형(Plex Mono)까지 한 패밀리에서 해결**된다. 이 프로토타입은 라벨에 모노스페이스를 많이 써서(LABEL 패턴) 같은 패밀리의 일관성이 중요했다.
- **IBM Plex Mono (라벨, 이벤트 로그)**: 데이터 필드 라벨과 dev panel의 이벤트 로그에 사용. 숫자가 정렬돼서 보이는 게 금융성 정보(₩89,000, 결제일)에 어울린다.

Inter나 Pretendard로 가지 않은 이유 — 이 둘은 요즘 한국 스타트업 UI의 "기본값"이 돼서, 쓰면 "흔한 AI 생성물"처럼 보일 위험이 있다. 포트폴리오는 기억에 남아야 하니까 한 단계 다른 선택을 했다.

### 색상 — 크림 베이지 + 테라코타 + 딥그린

```css
--bg: #f5f2ec;            /* 크림 베이지 */
--ink: #1a1915;           /* 검정에 가까운 따뜻한 잉크 */
--accent: #c2410c;        /* 테라코타 오렌지 (CTA) */
--success: #1f6b4a;       /* 딥그린 (active 상태) */
--warn: #a16207;          /* 머스터드 (해지 예정) */
--danger: #991b1b;        /* 버건디 (해지 버튼) */
```

**왜 흰 배경 + 파랑 CTA로 안 갔나.** 그게 제일 안전하고 제일 흔하다. 아동 도서 플랫폼이라는 컨텍스트에서 가장 기억에 남을 선택은 **책등 같은 크림 베이지 배경**. 거기에 테라코타 오렌지를 CTA 색으로 올리면 고서점 + 편집샵 분위기가 난다. 딥그린은 성공 상태(구독 중)에 — 식물/안정감을 연상시키고 오렌지와 보색 관계라 대비가 선명하다.

이 팔레트의 숨은 규칙: **어떤 색도 포화도 100%가 아니다.** 모든 색이 약간 탁한 쪽으로 빠져 있어서 긴 시간 봐도 눈이 안 아프다. 구독 관리 페이지는 사용자가 짜증 날 수 있는 순간(해지하려는 순간)에 보는 화면이다. 여기서 쨍한 색은 사용자를 더 자극한다.

### 상태 전이 표현 — `data-tone` 속성

```html
<div class="status-banner" data-tone="active">  <!-- 초록 -->
<div class="status-banner" data-tone="scheduled"><!-- 머스터드 -->
<div class="status-banner" data-tone="none">    <!-- 테라코타 -->
```

CSS에서:
```css
.status-banner[data-tone="active"]    { background: var(--success-soft); color: var(--success); }
.status-banner[data-tone="scheduled"] { background: var(--warn-soft); color: var(--warn); }
```

**왜 클래스 분기(.status-active, .status-scheduled)가 아닌가.** 속성 선택자(`[data-tone="..."]`)는:
1. 톤이 데이터 속성이라는 **의미가 마크업에 드러난다**. 클래스는 "이 요소는 이런 모습이다"를 말하고, data 속성은 "이 요소는 이런 상태다"를 말한다. status는 후자다.
2. JS에서 `el.dataset.tone = 'scheduled'`로 바꾸기 쉽다.
3. "is-active" 같은 BEM 수정자보다 확장성이 좋다 — 톤이 5개, 10개로 늘어나도 클래스 네이밍 전쟁이 안 난다.

실무 Tailwind 환경에선 이게 `data-[tone=active]:bg-success-soft` 같은 variant로 가지만, 원리는 같다.

## 4. 배운 것 — 해지 플로우 만들면서 걸린 함정들

이 프로토타입을 설계하고 구현하면서 실제로 한 번씩은 실수했던 것들.

### 함정 1. "낙관적 UI"에 대한 유혹

처음에 해지 버튼 클릭 → 바로 STEP_3로 전환 → 백그라운드에서 API 호출, 이렇게 짜려고 했다. 사용자 입장에서 빠르니까. 하지만 해지는 **금전적 신뢰 액션**이다. "해지됐어요" 라고 화면이 먼저 바뀌었는데 서버에선 실패해서 다음 달에 결제가 또 일어나면, 그 순간 고객 신뢰가 깨진다. 낙관적 UI는 좋아요 버튼 같은 거에 쓰는 것이다. 그래서 프로토타입에서도 "처리 중..." 상태를 800ms 넣어서, 응답 받은 다음 화면이 넘어가도록 했다.

교훈: **낙관적 UI를 고려할 땐 "실패했을 때 사용자가 느낄 감정의 무게"를 먼저 생각한다.** 좋아요 실패 = 살짝 아쉬움, 해지 실패 = 격분.

### 함정 2. `cancel_abandon` 계측의 누락

해지 모달을 열었다가 X 버튼으로 닫는 사용자를 **설계 문서에 쓰기 전까지는 잊고 있었다**. `cancel_flow_start`와 `cancel_success`만 잡으면 될 줄 알았다. 하지만 이 둘의 차이가 "해지 포기율"이다. 이걸 잡으려면 X 버튼 클릭 시점에 `cancel_abandon`을 발화해야 한다.

게다가 웹뷰에서는 사용자가 앱을 백그라운드로 보낸 채 그대로 두는 경우가 많아서, **일정 시간 아무 이벤트 없으면 자동으로 abandon을 발화**하는 로직까지 고려해야 한다. 프로토타입에는 단순화해서 X 버튼 클릭 시에만 발화하지만, 실서비스에선 `visibilitychange` 이벤트에 `pagehide`까지 묶어서 관리해야 한다.

교훈: **퍼널의 실패 경로는 성공 경로만큼 계측하지 않으면 나중에 개선 방향을 못 찾는다.** "왜 떨어지는지" 모르면 "떨어진다"는 사실만 안다.

### 함정 3. 사유 라디오에 기본값을 주고 싶은 유혹

초기 프로토타입에서 첫 번째 사유("콘텐츠가 기대와 달랐어요")에 기본 선택을 해뒀었다. 이러면 "다음" 버튼이 처음부터 활성화돼서 UX가 더 부드러워 보인다. 하지만 **이건 피드백 데이터를 오염시킨다**. 사용자의 35%가 귀찮아서 기본값을 그대로 내고 가버리면, 그 사유가 과대 집계된다. 라디오 버튼은 **반드시 사용자가 능동적으로 선택하도록** 해야 한다.

교훈: **UX 부드러움과 데이터 정합성이 충돌할 때, 데이터 정합성을 택한다.** 한 번 오염된 피드백 데이터는 프로덕트 의사결정을 몇 달씩 틀린 방향으로 끌고 간다.

### 함정 4. ESC 키로 모달 닫기를 안 만드는 습관

데스크톱 파워 유저에게 ESC는 당연한 기대다. 이걸 빼먹으면 "이 프로덕트 접근성 약하네"라는 미묘한 불신이 쌓인다. 프로토타입에는 `document.addEventListener('keydown', ...)` 한 줄로 넣었다. 실무에서는 포커스 트랩까지 같이 세트로 가야 한다 — 모달 안에서 Tab을 눌러도 모달 밖으로 포커스가 안 나가게.

### 함정 5. 혜택 재노출이 다크패턴이 되지 않게 하는 법

STEP_2(해지 확인) 화면에 "잊지 마세요, PLUS 회원에게만 있는 혜택" 박스를 넣었다. 이게 자칫하면 다크패턴이 된다. 다크패턴과 "한 번 더 생각하기 UI"의 차이는 **해지 버튼이 얼마나 찾기 쉬운가**다. 혜택 박스가 화면 70%를 차지하고, "해지 확정" 버튼이 작게 구석에 있으면 다크패턴. 혜택은 스크롤 없이 보이는 최소한만 노출하고, 해지 확정 버튼은 평소 버튼과 같은 크기여야 한다.

프로토타입에서는 혜택 박스를 `<ul>` 3줄로만 제한했고, "해지 확정" 버튼은 `.btn-danger`로 다른 버튼과 같은 크기다. 다만 색만 분리해서 "이건 되돌리기 어려운 액션이야"를 표현했다.

## 5. 만약 프로덕션에 올린다면

이 프로토타입은 포트폴리오용이라 단순화된 게 많다. 실제로 우따따 같은 서비스에 올린다면 이 수준에서 추가될 것들:

1. **상태 전이 다이어그램을 코드로** — XState나 useReducer로 명시적 state machine. `ACTIVE → CANCEL_SCHEDULED` 같은 전이를 데이터로 관리.
2. **Apollo Mutation + optimistic response의 정교한 사용** — 해지는 낙관적 X지만 결제수단 변경은 낙관적 O 같은 구분.
3. **GA4 이벤트를 타입 세이프하게** — `track('cancel_flow_start')` 같은 함수가 실수한 이벤트명을 허용하지 않도록 제네릭으로 이벤트 카탈로그 타입을 정의.
4. **Playwright E2E** — 해지 3스텝을 전체 다 찍는 테스트 시나리오. 이력서에 언급한 Playwright 도입 경험이 바로 이 영역에서 빛난다.
5. **웹뷰 환경 분기** — Apple/Google 결제 사용자는 해지 버튼 대신 "앱스토어에서 해지" 안내. WebView Bridge로 OS 판별해서 분기.

## 6. 이 문서가 FORBBURNJI라고 이름 붙은 이유

이 프로젝트의 주인(bburnji)이 모든 프로젝트마다 자동으로 이런 기술 문서를 남기기로 했기 때문이다. 프로젝트마다 기억은 휘발되지만, 문서는 남는다. 6개월 뒤 이 폴더를 다시 열었을 때 "내가 그때 왜 이렇게 했더라?"를 이 문서 하나로 복원할 수 있어야 한다. 그게 이 파일의 존재 이유다.
